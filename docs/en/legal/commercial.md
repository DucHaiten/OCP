# Commercial Terms OCP-OCL v1.0

This document explains the commercial path of OCP-OCL in a way that users and organizations can read in order to make an initial decision.

The goal of this file is not to replace a specific commercial agreement.  
Its goal is to clarify:
- when you should discuss the commercial path;
- what role that path serves;
- what must not be inferred unless there is a separate written agreement.

## Short Summary

If you only need the quick conclusion, these are the four most important points:

1. OCP-OCL follows a `dual-license` model.
2. The OSS side remains `AGPL-3.0-only`.
3. The commercial path does not automatically apply just because you are a company or just because your use has a commercial context.
4. If you need terms that differ from the OSS side, you must go through a separate commercial agreement.

## 1) What is the commercial path of OCP-OCL?

The commercial path is a separate licensing route for cases that do not want to use, or cannot use, OCP-OCL only under the OSS side.

In plain language:
- if you use the OSS path, you read and comply with `LICENSE`;
- if you need different terms, you must not assume the project already grants them by default;
- you are only on the commercial path if there is a separate commercial agreement in place.

The point that needs to be understood clearly:
- this file does not itself grant you a commercial license;
- this file only explains when the commercial path is relevant and how to understand its scope safely.

## 2) When should I discuss the commercial path?

You should move to the commercial path if one or more of the following applies:

- you want to distribute, embed, or integrate OCP-OCL into a proprietary product;
- you need separate legal terms for an organization, company, or procurement process;
- you need support committed in writing;
- you need SLA, warranty, indemnity, or similar enterprise-style terms;
- you need a clearly documented licensing position for legal, audit, or internal purchasing review;
- you need an exception that the OSS path does not provide.

In short:
- if you read `LICENSE` and conclude that the OSS path does not fit your intended use model, that is a clear signal to move to a commercial discussion.

## 3) Which cases are usually a better fit for the OSS path?

Being an organization, or having some commercial aspect, does not automatically mean you must buy a commercial license.

Based on current public docs, the following situations often start with the OSS path:
- learning, research, and technical evaluation;
- internal experimentation;
- an open-source project that is compatible with the license;
- use cases that do not require separate legal terms or separate support commitments.

The important point is:
- you must not infer “internal company use always means buying is mandatory”;
- but you also must not infer “internal use definitely means the license does not matter”.

Each case still needs to be evaluated based on actual needs and the ability to comply with the OSS side.

## 4) What does the commercial path promise today, and what does it not promise?

### 4.1) What this file can say clearly

The commercial path exists to support cases that need:
- licensing terms different from the OSS side;
- legal terms suitable for organizations or companies;
- support packages or operational commitments defined more clearly;
- a clean path for procurement and compliance.

### 4.2) What this file does not promise automatically

This file does not mean:
- every organization using OCP-OCL must buy;
- every enterprise use case automatically gets an exception;
- a price list, SLA, or warranty is already available for everyone by default;
- reading this file alone gives you a valid commercial license.

To have rights and obligations under the commercial path, there must be a separate approved agreement.

## 5) What applies if there is no separate commercial agreement yet?

If there is no separate confirmed commercial agreement, the safe reading is:
- you are not yet on the commercial path;
- your use still has to be evaluated under the OSS side and the `LICENSE` file.

This point matters a lot because it prevents common misunderstandings.

You should not infer things such as:
- “I plan to buy later, so I already count as commercial now”;
- “I am talking to the project, so I can assume a temporary exception already exists”;
- “my organization will probably pay anyway, so AGPL does not matter during this stage”.

If there is no written or otherwise explicit commercial confirmation, you should not assume the commercial exceptions already exist.

## 6) How do `commercial.md`, `licensing.md`, and `LICENSE` relate to each other?

These three files serve different purposes:

### `LICENSE`
- the original OSS license text;
- the place to read the legal obligations of the open-source path.

### `docs/en/legal/licensing.md`
- explains the overall picture:
  - what license OCP-OCL uses;
  - what dual-license means;
  - when you should evaluate the OSS path and when you should move to the commercial path.

### `docs/en/legal/commercial.md`
- explains the commercial path itself:
  - which cases should move into a commercial discussion;
  - what can reasonably be expected;
  - what must not be inferred without a separate written agreement.

In short:
- `LICENSE` is the legal source for the OSS side;
- `licensing.md` is the overall explanation;
- `commercial.md` is the dedicated explanation of the commercial path.

## 7) How does the commercial path relate to the CLA and contribution policy?

Under current policy:
- external contribution requires a CLA;
- the project locks `cla_type = license_grant`;
- the outbound model is `AGPL-3.0-only+commercial`.

Operationally, this means:
- the project keeps the ability to continue publishing the OSS side;
- while also retaining the rights needed to operate the commercial path lawfully.

For a commercial user, the practical meaning is:
- the commercial path is not an improvised verbal promise;
- it is tied to a contribution and licensing model that is already locked in the repo.

## 8) What should the project avoid saying vaguely?

These are examples of wording that should not be used unless a separate written policy says so clearly:

- “free for small users, mandatory payment for large users”;
- “every organization must buy a commercial license”;
- “internal use is always exempt from license obligations”;
- “if you pay, all other conditions disappear”.

If the project later adopts a more specific commercial policy, it should be written explicitly in the legal docs and/or the corresponding agreement, not left to reader guesswork.

## 9) If I am considering the commercial path, what should I do?

The safe order is:

1. Read `LICENSE` to decide whether the OSS side fits.
2. Read `docs/en/legal/licensing.md` to understand the overall model.
3. If you need different terms, treat that as the signal to move to the commercial path.
4. Only treat the commercial path as effective when there is a separate confirmation or agreement.

At the current public-doc snapshot, this file mainly helps you determine:
- whether you should move into a commercial discussion;
- and how not to interpret the commercial path too broadly or too vaguely.

## 10) Limits of this document

This file is an explanation document for readers.

It is not:
- a full commercial agreement;
- a price quote;
- a default support/SLA commitment;
- legal advice.

If you are making a decision with real legal, financial, or procurement consequences, you should:
- read `LICENSE`,
- read `licensing.md`,
- and only treat the commercial path as effective when there is a separate approved document.

## 11) Conclusion

The most practical reading is:
- OCP-OCL has a commercial path, but that path does not arise automatically;
- the OSS side remains the default if no separate agreement exists;
- the commercial path exists to handle needs that do not fit the OSS side;
- any separate exception or commercial right must be confirmed explicitly and must not be inferred.
